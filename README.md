# REA와 직접 만든 도구로, 서비스가 끝난 모바일 게임의 서버를 오프라인으로 되살려 본 개인 연구

「영원한 7일의 도시」는 도시를 짓고 영웅을 키우며 7일을 되풀이하는 이야기를 진행하는 모바일 게임입니다. 서비스가 끝났고 서버 소스도 서버 쪽 데이터도 남아 있지 않습니다. 남은 것은 클라이언트 앱과 2021년에 기록된 네트워크 캡처, 당시 기기 백업입니다. 이 연구는 그 자료를 바탕으로 서버를 다시 만들어 게임이 로그인부터 도시, 스토리, 영웅 육성, 던전류와 이벤트 콘텐츠까지 진행되게 할 수 있는지 확인한 기록입니다. 서버를 PC 없이 기기 안에서 돌리는 구성도 만들었습니다.

작업은 2026년 5월에 Ghidra를 비롯한 일반 분석 도구와 스크립트로 시작했습니다. 10월 12일에 역공학 도구 REA를 들여와서 캡처와 네이티브 라이브러리를 읽는 일을 맡겼습니다. REA는 네이티브 분석, HTTP 캡처 판독, 기기 조작 기능을 제공합니다. 게임 스크립트와 게이트 구간은 REA 범위 밖이어서 따로 만든 도구 사슬로 읽었습니다. 소스 코드와 게임 데이터, 근거 파일(영상, 스크린샷, 로그)은 올리지 않았고 이 저장소에는 방법과 근거에 대한 설명만 있습니다.

| 질문 | 답 |
|---|---|
| 무엇을 했나 | 원본 서버 없이 클라이언트가 요구하는 응답을 다시 구현했습니다. 부팅, 로그인, 도시 진입은 실기기에서도 확인했고 그 뒤 콘텐츠는 에뮬레이터에서 일부만 확인했습니다(아래 상태 표). |
| 왜 어려웠나 | 서버 소스가 없고, 정답으로 쓸 자료는 로그인 구간의 HTTP 캡처뿐입니다. 게임 플레이 구간의 서버 응답은 한 건도 남아 있지 않아서 클라이언트에 든 코드와 표에서 거꾸로 알아내야 했습니다. |
| 범위 | 1인 프로젝트입니다. 산출물은 서버, 복원 도구, 검증 도구, 테스트, 분석 문서 전부입니다. |
| 확인 방법 | 캡처가 있는 정적 응답은 원본 바이트 그대로 돌려주고 길이와 SHA-256으로 고정했습니다. 캡처가 없는 게이트 구간은 클라이언트 로그에 남는 증상만 보고 서버 응답 네 가지를 맞춰 도시 화면을 열었습니다. |

## 연구 질문과 REA의 역할

서버를 볼 수 없는 온라인 게임을 클라이언트와 오래된 캡처만으로 어디까지 되살릴 수 있는가가 질문입니다. 클라이언트와 캡처의 문자열을 보면 원본 서버는 게이트, 게임, DB로 나뉜 분산 구조였던 것으로 추정됩니다. 클라이언트에는 서버를 부르는 코드와 표, 계산 코드가 남아 있어서 서버가 어떤 값을 어떤 순서로 돌려줘야 하는지는 거기서 읽어 냅니다.

REA는 그 읽기 중에서 캡처와 네이티브 라이브러리, 기기 조작을 맡았습니다. 5월의 첫 도시 진입은 REA 없이 이뤄졌습니다. 10월 12일에 응답을 2021 캡처 원본으로 되돌릴 때는 REA가 판독한 캡처 4세트의 건수와 해시를 인용했습니다. 게이트 구간의 응답 값은 대부분 클라이언트 스크립트에서 나왔고 REA의 몫은 캡처 판독과 네이티브 라이브러리 확인에 있었습니다.

| REA로 한 일 | 결과 |
|---|---|
| 네이티브 라이브러리 분석 | 39MB ARM64 라이브러리를 Ghidra로 열어 프로시저 77,279개, 문자열 52,708개를 얻었습니다. 첫 분석은 13분 58초였고(호스트 RAM 13GB, 분석 프로세스 최대 3.0GB, 에뮬레이터 동시 실행). 그래서 이 라이브러리는 분석 결과를 한 번 만들어 이어서 조회하는 규칙을 세웠습니다. |
| HTTP 캡처 판독 | 2021 캡처 4세트(512건)를 HAR로 바꿔 읽혔습니다. 변환기는 따로 만들었습니다. 게스트 로그인 세트 106건 중 응답 본문이 있는 96건에서 REA가 계산한 SHA-256이 원본 캡처의 값과 모두 같았습니다. |
| 요청 정리 | 4세트의 요청을 호스트 30개, 44묶음으로 정리했습니다. 이 가운데 게임 관련 22묶음은 모두 경로가 확인됐습니다. |
| 기기 조작 도구 검증 | 파일을 넣고 앱을 설치하고 실행하는 도구를 에뮬레이터에서 실제로 호출해 확인했습니다. |

REA가 다루지 못하는 것은 게임 스크립트(NeoX 엔진)와 게이트 구간의 패킷 캡처입니다. 이 부분은 공개된 디컴파일러, 기기 조작 도구와 이 연구에서 만든 도구를 조합해 읽었고, 뒤의 「복원 방법과 서버 구조」에서 설명합니다.

### 지금 어디까지 되는가

정답지는 서버 응답이 맞는지 판정할 기준 자료를 뜻합니다. HTTP 구간에는 2021 캡처가 있고, 게이트 이후에는 없습니다. 던전류는 정신력을 쓰는 여러 도전 콘텐츠를, 회차는 이야기를 끝까지 한 번 마친 한 판을 가리킵니다.

| 구간 | 정답지 | 에뮬레이터 | 실기기 |
|---|---|---|---|
| 업데이트 확인, 로그인(HTTP) | 2021 캡처 | 확인 | 실기기 확인 |
| 게이트 접속, 도시 진입 | 없음 | 확인 | 실기기 확인. 휴대폰은 5월 캡처에서 게이트 연결이 0건이었다 |
| 프롤로그, 도시 7일 반복, 엔딩과 다음 회차 | 없음 | 3회차 진입까지, 엔딩은 실패 쪽 2개만. 정식 결말은 못 봄 | 못 봄 |
| 영웅 육성, 던전류 | 없음 | 종류마다 한 바퀴. 전투는 검증용 조정을 건 상태로 이김 (무조정 승리 1건) | 실기기 확인 없음 |
| 이벤트 | 없음 | 종류마다 한 바퀴 확인한 것과 단위 테스트만 거친 것을 구분해 적음 | 못 봄 |
| 서버 PC 없이 단독 실행 | 해당 없음 | 확인 | 설치와 실행 확인 |

에뮬레이터 확인은 기기 조작 도구로 화면을 조작하고 서버 로그와 클라이언트 엔진 로그의 상태 전이로 판정했습니다. 태블릿의 도시 확인은 시험용으로 만든 계정 상태를 복사해 쓴 것입니다. 정답지가 없는 구간은 클라이언트가 읽는 필드와 순서를 소스에서 뽑아 규칙을 세웠고, 그 규칙이 표에서 나온 값인지 추론인지는 추론 표시로 구분했습니다. 영상과 스크린샷은 이 저장소에 없습니다.

## 복원 방법과 서버 구조

작업은 네 단계를 돕니다. 캡처와 클라이언트에서 사실을 뽑고, 그 사실로 규칙을 구현하고, 규칙이 클라이언트의 요구와 맞는지 자동으로 대조하고, 마지막에 에뮬레이터 화면과 로그로 확인합니다.

```
2021 HTTP 캡처 ──(HAR 변환, REA 판독)──────────────┐
                                                    ├─> 서버 규칙 구현 ──> 가짜 클라이언트 테스트 ──> 에뮬레이터·기기
클라이언트 스크립트 ──(읽을 수 있는 형태로 복원)──┤
                                                    └─> RPC 목록 · 데이터 표(JSON)
```

### 복원 서버를 이루는 것

| 구성 요소 | 하는 일 |
|---|---|
| 연결 구조 | 게임 접속을 HTTP 서비스와 게이트 서버로 나눠 받습니다. |
| HTTP 서비스 | 설정, 업데이트 확인, 로그인, 결제, 텔레메트리에 답합니다. 캡처에 있는 응답은 바이트와 Content-Type까지 그대로 돌려줍니다. |
| 게이트 서버 | 로그인 뒤 게임 통신을 받는 asyncio 기반 원시 TCP 서버입니다. 길이 접두 프레임 안에 protobuf 메시지가 들어 있고 스트리밍 압축이 걸립니다. 이 문서는 압축 이외의 선로 처리를 다루지 않습니다. |
| 아바타 계층과 RPC 핸들러 | 접속한 계정 하나의 호출(RPC)을 받습니다. 핸들러에 표시만 해 두면 이름 그대로 호출에 연결됩니다. 핸들러가 없는 호출은 로그만 남기고 빈 결과로 풀어서 클라이언트가 잠기지 않게 합니다. |
| 게임 규칙 모듈 | 도시, 영웅 육성, 장비, 던전류, 이벤트를 기능별로 나눈 규칙입니다. 클라이언트에서 뽑은 표, 계정 상태, 서버 시계를 입력으로 받습니다. |
| 상태 저장 | 계정마다 JSON 파일 하나입니다. 임시 파일에 쓴 뒤 교체하고 깨진 파일은 따로 옮겨 둡니다. |
| 복원 도구 | 클라이언트 스크립트를 읽을 수 있는 형태로 되돌린 뒤 서버 호출 목록 1,334개와 서버용 데이터 JSON(원본 표 여러 개를 묶은 것)을 뽑습니다. |
| 앱 안 서버 | 기기 안에서 서버를 게임과 다른 프로세스로 실행합니다. 앱 안 VPN으로 게임 접속을 서버에 잇습니다. |

### 도시 진입 한 건을 따라가기

5월 22일에 마지막으로 푼 문제입니다. 클라이언트는 로그인 뒤 게이트 서버에 TCP로 붙고, 서버가 다음 순서로 답해야 도시 화면이 열립니다.

1. 접속 요청에 접속 응답을 보냅니다.
2. 계정 엔티티(서버와 클라이언트가 함께 들고 있는 객체)를 먼저 만들어 보냅니다. 클라이언트가 이걸 받아야 상태가 로그인 단계로 넘어갑니다.
3. 클라이언트가 로그인 정보를 보내면 그 계정의 아바타 엔티티를 만들어 스냅샷(계정 상태 묶음)과 함께 보냅니다.
4. 플레이 전환을 알리고, 클라이언트가 보내는 상태 전환, 이벤트 조회, 생존 신호에 각각 맞는 모양으로 답합니다.

각 단계에서 틀리면 클라이언트 로그에 증상이 남았습니다. 상태 전이 경로를 찾지 못한다는 경고는 서버가 계정 엔티티를 보내지 않았다는 뜻이었습니다. 처음에는 접속 응답이 전이를 일으킨다고 가정했다가 로그의 전이 경로 정의를 보고 반증했습니다. 이벤트 조회에 답하지 않으면 로딩 화면이 약 16초 뒤 타임아웃으로 재접속을 반복했고, 생존 신호에 답하지 않으면 약 30초 뒤 클라이언트가 스스로 로그아웃했습니다. 상태 전환 요청에 답하지 않으면 약 15초 뒤 접속이 끊겼으며, 응답에 요청값을 되돌려야 한다는 점은 해당 코드를 디스어셈블해서 확인했습니다. 이 네 가지를 맞춘 서버가 5월에 도시 화면에 이르렀습니다. 10월 12일에 기준선(에뮬레이터가 정해진 단계를 통과하던 상태)을 복구한 뒤에는 접속 1회로 생존 신호가 5초 간격으로 이어지는 것을 다시 확인했습니다.

## 결정과 대안

**응답을 어디까지 원본 그대로 둘 것인가.** 5월 실기기에서 업데이트 확인 응답의 호스트를 IP로 바꿨더니 클라이언트가 업데이트 확인에서 멈췄습니다. 그래서 정답지가 있는 응답은 캡처 원본을 바이트와 Content-Type까지 그대로 돌려주기로 했습니다. 게이트 구간에는 캡처가 없어서 같은 방법을 쓸 수 없고, 거기서는 클라이언트 로그의 증상이 유일한 검증 수단이었습니다.

**규칙을 어디서 읽을 것인가.** 처음에는 클라이언트의 호출 지점을 하나씩 디스어셈블해 상수 이름을 추측했습니다. 스크립트 전체를 읽을 수 있는 소스로 되돌리면 필드, 타입, 순서를 한꺼번에 반복해서 확인할 수 있어서 그쪽으로 옮겼습니다. 복원이 틀리면 그 위에 세운 서버 규칙이 모두 어긋나기 때문에 복원 도구에는 따로 검증하는 도구를 붙였습니다. 게임 스크립트 13,462개를 Python 소스로 복원했고, 부분 실패는 5개입니다.

**온라인 전투는 어떻게 할 것인가.** 전투 서버의 규칙도 클라이언트에서는 알 수 없었습니다. 그래서 온라인 전투가 필요한 콘텐츠는 클라이언트가 전투를 직접 계산하게 돌려보냈습니다. 판마다 자동 전투 버튼을 눌러야 하는 콘텐츠가 생겼습니다.

## 막혔던 일

**기준선이 무너져 있던 날.** 10월 12일에 서버 응답, 호스트 설정, DNS, 인증서, 패킷 캡처 설정을 점검하자 원본과 어긋난 곳이 나왔습니다. 응답과 호스트 설정이 2021 캡처 원본에서 벗어나 있었고, 패킷 캡처 인터페이스는 엉뚱한 곳에 걸려 있었습니다. 응답을 2021 캡처 원본으로 되돌리고 DNS, 인증서, 캡처 설정을 다시 만든 뒤, 응답 길이와 해시를 테스트로 고정하고 캡처 재생 대조기를 만들었습니다. 같은 어긋남이 다시 생기지 않게 하는 장치입니다.

**로그인이 안 되는 원인을 잘못 짚었던 일.** 5월에 로그인 실패의 원인을 게이트 서버 미구현이라고 가정했습니다. 전 포트 패킷 캡처를 걸어 보니 연결 28개가 전부 TLS였고 게이트로 가는 연결은 0건이었습니다. 확정된 원인은 서버 목록 응답이 13바이트짜리 스텁이었던 것입니다. 이를 고치자 다음 단계에서 서버명 없는 TCP 접속이 HTTPS 서버로 가던 중계 설정이 두 번째 막힘으로 드러났습니다.

**게임만 껐다 켜면 서버에 붙지 못하던 일.** 앱 안 서버에서, 게임 프로세스만 종료하고 다시 켜면 접속이 안 됐습니다. 서버가 듣던 소켓을 안드로이드가 닫아 버려서 수락 대기 호출이 초당 약 4천 번씩 실패하고 있었습니다. 원인은 전날 만든 기기 안 로그에서 찾았습니다. 서버가 닫힌 소켓을 스스로 다시 열게 했고 접속 화면이 단계적으로 재시도하게 했습니다. 이전 테스트는 항상 두 프로세스를 함께 종료해서 이 경우를 시험한 적이 없었습니다.

**로그 마스킹을 적용했다.** 앱 안 로그를 파일에 쓰기 전에 민감한 값을 가리도록 바꿨습니다.

## 얼마나 믿을 수 있나

사용자 지표가 없는 연구라서, 결과가 맞다는 근거를 정답지가 있는 곳과 없는 곳으로 나누어 적습니다.

캡처가 있는 응답은 바이트 단위로 맞춥니다. 캡처 재생 대조기는 캡처 세트마다 엔드포인트 17~21묶음을 재생해 같음 12~16, 일부 일치 1, 다름 3~4, 상태 차이 1을 냈습니다. 다름은 로그인 토큰, 접수 번호, 호출자 주소처럼 요청마다 달라지는 응답과 캡처 안에서도 순서가 흔들리는 응답 두 가지입니다. 서버가 캡처 응답을 그대로 돌려주도록 만들었으므로 이 일치는 독립된 검증이 아니라 구현이 의도대로 됐는지의 확인입니다. 정적 응답은 길이와 SHA-256을 테스트로 고정했고, 변환기를 거친 게스트 로그인 세트에서는 응답 본문 96건의 해시가 모두 일치했습니다.

정답지가 없는 곳은 클라이언트가 읽는 값을 정답으로 씁니다. 능력치 계산은 복원한 클라이언트 소스의 계산 코드를 옛 Python 환경에서 따로 실행한 값과 비교했습니다. 무작위로 만든 계정 상태 40개(영웅 160건)과 장착 보구 492개에서 오차 1e-9 이내로 일치했습니다. 서버의 계산이 이 코드를 옮긴 것이라서 이 대조는 독립 검증이 아니라 옮기는 과정의 실수를 잡는 용도입니다. 서버가 보내는 호출 전체를 복원한 클라이언트 스텁과 대조하는 가짜 클라이언트가 테스트로 돌고, 잘못된 키 이름을 잡아낸 사례가 있습니다.

같은 서버 코드를 PC에서 진짜 FastAPI와 기기 구성(Python과 대체 패키지) 두 가지로 돌려 응답 119건을 비교했을 때 같음 113, 알려진 차이 6, 문제 0이었습니다. 알려진 차이 6의 원인은 아직 확인하지 못했습니다.

서버 호출 1,334개 중 핸들러가 584개 있습니다. 정적으로 센 값이고, 기능이 동작한다는 뜻은 아닙니다.

## 테스트와 검증 규칙

2026-10-25에 Windows PC에서 서버 테스트를 다시 돌렸더니 4,003개 통과, 5개 실패, 2개 오류, 3개 건너뜀이었고 90.28초가 걸렸습니다. 이 수치는 줄바꿈이 CRLF인 Windows 체크아웃 기준입니다. 실패 5개 가운데 3개는 기기 구성의 소켓 테스트이고, 2개는 CRLF로 저장된 정적 응답의 바이트 대조입니다. 오류 2개는 길이가 매우 긴 매개변수를 넣은 시험에서 났습니다. 원인은 아직 확인하지 못했습니다. 운영 환경인 Ubuntu에서는 다시 돌리지 않았습니다. 서버 시계와 난수 시드는 테스트에서 고정해서 결과가 재현되게 했고, 실제 소켓을 여는 테스트는 게이트 서버와 앱 안 서버 쪽에만 있습니다.

서버 응답을 바꾸려면 HTTP 구간에서는 패킷 캡처와 클라이언트 소스를, 게이트 구간에서는 클라이언트 소스를 확인해야 하고, 회귀 테스트를 1개 이상 추가해야 합니다.

## 아직 모르는 것과 한계

원본 서버가 하던 일 가운데 클라이언트에 흔적이 없는 부분은 모릅니다. 서버만 아는 밸런스 값과 전투 정산이 여기에 해당하고, 다른 플레이어가 있어야 뜻이 있는 이벤트와 순위는 "나 혼자"인 형태로 줄였습니다. 게이트 구간에는 2021 캡처가 없어서 응답의 순서와 값 대부분이 클라이언트 소스에서 거꾸로 세운 추론입니다.

전투 정산은 콘텐츠마다 구현 정도가 다릅니다. 던전류는 정산과 보상 지급을 구현했고, 행동과 구역 전투의 보상, 회차 끝 보상, 사건 보상은 비어 있습니다. 온라인 전투가 필요한 콘텐츠 일부는 부분적으로만 됩니다. 정식 결말은 아직 하나도 화면으로 확인하지 못했습니다. 이벤트는 종류마다 한 바퀴 확인한 것과 단위 테스트만 거친 것을 구분해 적었습니다.

앱 안 서버는 64비트 기기와 일정 버전 이상의 안드로이드가 필요하고, VPN 허용이 필요하며, 다른 VPN과 같이 쓸 수 없습니다. 기기에 올려 둔 빌드가 가장 최근 서버 수정을 항상 담고 있지는 않습니다.
